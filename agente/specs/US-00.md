## 1. Historia de usuario

**Como** equipo de desarrollo, **quiero** una especificación general aprobada y un entorno reproducible, **para** que todas las historias posteriores se especifiquen, construyan y prueben sobre la misma base.

## 2. Propósito

Historia técnica que habilita el ciclo Spec-Driven Development: fija la visión del producto en `specs/00-producto.md`, el formato de reglas en `specs/formato-reglas.md`, la plantilla de spec y el entorno (repositorio, CI, Docker Compose, datos de prueba) sobre el que se implementa el walking skeleton.

## 3. Alcance

**Incluye**

- `specs/00-producto.md`: objetivo, actores, alcance, entradas/salidas, RNF-01..07 y ALT-01..12.
- `specs/formato-reglas.md` con el JSON Schema de una regla y el ejemplo RE-20.
- `specs/_template.md` (propósito, entradas, salidas, reglas, excepciones, AC, pruebas).
- Repositorio GitHub con `app/`, `specs/`, `rules/`, `prompts/`, `tests/`, `docs/`.
- Docker Compose (FastAPI + PostgreSQL) que arranca con un comando; README de arranque. Celery + Redis se incorporan en una fase posterior (decisión de revisión D-04).
- GitHub Actions ejecutando Pytest en cada push y pull request.
- Cinco PDFs de prueba anonimizados: 2 con figuras problemáticas, 1 sin figuras, 1 escaneado, 1 correcto.
- Plantillas oficiales (Word y LaTeX) e `innosoft.cls` guardadas en `docs/`.

**No incluye**

- Funcionalidad de negocio (la aportan US-01 en adelante).
- Despliegue en servidor de la revista.

## 6. Reglas de comportamiento

1. Ninguna historia pasa a implementación sin spec en estado *Aprobada* (revisada por el otro developer).
2. Las credenciales (Gemini, OJS) se leen de variables de entorno; nunca se versionan.
3. Los PDFs de prueba no contienen datos personales reales (nombres, correos, ORCID sustituidos).
4. La rama `main` está protegida: solo se integra por pull request con CI en verde.

## 8. Criterios de aceptación

**AC-01**

```gherkin
Dado el repositorio clonado en una máquina limpia con Docker
Cuando se ejecuta `docker compose up`
Entonces la API responde `200` en `GET /health` y la base de datos acepta conexiones
```

**AC-02**

```gherkin
Dado un pull request con una prueba fallida
Cuando se ejecuta GitHub Actions
Entonces el check de CI queda en rojo y el merge está bloqueado
```

**AC-03**

```gherkin
Dado `specs/00-producto.md`
Cuando ambos developers la revisan
Entonces queda en estado *Aprobada* con los RNF-01..07 y ALT-01..12 enumerados
```

**AC-04**

```gherkin
Dado la carpeta `tests/fixtures/pdfs/`
Cuando se inspecciona
Entonces contiene los 5 PDFs descritos y ninguno incluye correos u ORCID reales
```
