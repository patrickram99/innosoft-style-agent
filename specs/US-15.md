## 1. Historia de usuario

**Como** editor, **quiero** que cada incumplimiento se convierta en una sugerencia redactada en español claro y cordial, **para** poder enviarla al autor casi sin editar.

## 2. Propósito

Transforma hallazgos técnicos en observaciones comprensibles para el autor, manteniendo la trazabilidad `rule_id` y sin que el LLM decida qué es un incumplimiento (eso lo decide el motor).

## 3. Alcance

**Incluye**

- Prompt versionado en `prompts/sugerencia/vN.md` con instrucciones de tono y formato.
- Llamada a Gemini con salida JSON estructurada `{rule_id, sugerencia, ejemplo_corregido?}`.
- `temperature ≤ 0,3`; modelo y versión de prompt configurables.
- Persistencia de la sugerencia con `origen=llm`, `prompt_version` y `model`.

**No incluye**

- Validación del esquema y reintento (US-16).
- Anonimización (US-17, requisito previo).
- Reintentos por red y presupuesto de tokens (US-18).

## 4. Entradas

| Entrada | Origen / formato | Restricciones |
|---|---|---|
| Hallazgo | US-10..US-14 | Todo hallazgo tiene la forma `{rule_id, severidad, página, ubicación, evidencia, valor_encontrado, valor_esperado}` y referencia una regla existente en `rules/innosoft/*.yaml`. |
| Regla | US-09 | `descripcion`, `mensaje`, `fuente`. |
| Fragmento anonimizado | US-17 | ≤ 600 caracteres alrededor del hallazgo. |

## 5. Salidas

| Salida | Destino / formato | Descripción |
|---|---|---|
| Sugerencia | Tabla `suggestions` | `{id, finding_id, rule_id, sugerencia, ejemplo_corregido, origen, prompt_version, model, created_at}` |
| Estado del manuscrito | `ready_for_review` | Cuando todos los hallazgos tienen sugerencia. |

**Contrato de ejemplo**

```json
{"rule_id": "RE-42",
 "sugerencia": "Le sugerimos citar las referencias múltiples por separado, de acuerdo con el estilo IEEE de la revista.",
 "ejemplo_corregido": "…en estudios previos [1], [3], [5]."}
```

## 6. Reglas de comportamiento

1. El prompt incluye: rol (asistente editorial de Innosoft), la regla con su fuente, el hallazgo (encontrado/esperado) y el fragmento anonimizado; nunca el PDF completo.
2. Tono: español formal, trato de *usted*, cordial, sin culpabilizar; máximo 80 palabras por sugerencia.
3. El LLM no puede crear, fusionar ni descartar hallazgos: una llamada produce exactamente una sugerencia por hallazgo recibido.
4. `ejemplo_corregido` solo cuando el fragmento lo permite (citas, referencias, pies de figura); se omite para tamaño o DPI de figuras.
5. Los hallazgos marcados `requires_llm` indican en el prompt que el editor debe verificar la observación.
6. Todo cambio de prompt crea una nueva versión en el repositorio (RNF-07).

## 7. Excepciones y flujos alternativos

| Condición | Comportamiento esperado | Ref. |
|---|---|---|

| Hallazgo sin fragmento de texto (p. ej. figura) | El prompt se construye solo con los metadatos del hallazgo. | — |

## 8. Criterios de aceptación

**AC-01**

```gherkin
Dado un hallazgo RE-20 de una figura de 300 × 600 px
Cuando se genera la sugerencia
Entonces el JSON contiene `rule_id=RE-20` y un texto en español que menciona el tamaño mínimo
```

**AC-02**

```gherkin
Dado la configuración del cliente
Cuando se inspecciona la llamada
Entonces `temperature` es ≤ 0,3 y se registra `prompt_version`
```

**AC-03**

```gherkin
Dado un manuscrito con 12 hallazgos
Cuando termina la generación
Entonces existen 12 sugerencias, cada una con el `rule_id` de su hallazgo
```

## 10. Notas de diseño

- Usar el modo de salida JSON con esquema de respuesta de la API de Gemini.
- Agrupar varios hallazgos del mismo manuscrito en una sola llamada es una optimización posible; la spec exige correspondencia 1 a 1 en la salida.
